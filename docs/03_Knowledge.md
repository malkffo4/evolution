# Knowledge

Version: 1.0

---

# Назначение

Данный документ определяет внутреннюю модель знаний NeuroCore.

Это один из самых важных документов проекта.

Все остальные подсистемы — Memory, Reasoning, Planner, VM, Learning, Execution — работают исключительно через модель знаний, описанную здесь.

Если меняется модель знаний, меняется практически вся система.

Поэтому любые изменения этого документа должны быть тщательно обоснованы.

---

# Что такое знание

Для NeuroCore знание — это минимальная логически завершённая единица информации, которую система способна:

- сохранить;
- понять;
- использовать;
- изменить;
- связать с другими знаниями;
- объяснить;
- удалить.

Знание является фундаментальным объектом всей архитектуры.

Внутри системы не существует других типов информации.

После прохождения через Perception и Understanding любая информация становится знаниями.

---

# Что НЕ является знанием

Следующие вещи сами по себе знаниями не являются.

Текст.

PDF.

HTML.

Изображение.

Видео.

Речь.

JSON.

Исходный код.

XML.

Markdown.

Все перечисленные объекты являются лишь источниками информации.

После обработки они исчезают как самостоятельные сущности.

В системе остаются только знания.

---

# Главный принцип

Внутри NeuroCore существует только один универсальный объект.

```
Knowledge Object
```

Любая информация внутри памяти должна существовать именно в таком виде.

Не допускается создание специальных внутренних объектов только для отдельных подсистем.

Memory не имеет собственных форматов.

Reasoning не имеет собственных форматов.

Planner не имеет собственных форматов.

VM не имеет собственных форматов.

Все работают с одинаковыми объектами знаний.

---

# Почему используется единая модель

Большинство систем разделяют данные.

Например:

```
Текст

↓

Отдельная структура

Изображение

↓

Другая структура

Код

↓

Третья структура
```

В результате появляется множество несовместимых представлений.

NeuroCore использует другой подход.

```
Любой источник

↓

Understanding

↓

Knowledge Object
```

После этого различий больше не существует.

Для памяти одинаково выглядят:

- определение;
- функция;
- рецепт;
- статья;
- математическая теорема;
- структура данных;
- рецепт приготовления пищи;
- SQL-запрос;
- описание протокола.

Различается только их содержимое.

---

# Требования к модели знаний

Модель знаний должна удовлетворять следующим требованиям.

## Универсальность

Любое знание должно храниться в одном формате.

---

## Расширяемость

Добавление нового типа знания не должно требовать изменения архитектуры памяти.

---

## Независимость

Knowledge Object не зависит:

от LMDB;

от графа;

от Python;

от LLM;

от VM;

от способа хранения.

---

## Самоописание

Каждый объект содержит достаточно информации, чтобы быть понятным без обращения к исходному источнику.

---

## Прослеживаемость

Каждый объект обязан хранить происхождение.

Система всегда должна знать:

откуда появилось знание;

когда оно появилось;

каким способом было получено.

---

## Изменяемость

Любой объект может изменяться.

При этом сохраняется история изменений.

---

## Объяснимость

Любое решение должно иметь возможность сослаться на знания, участвовавшие в его построении.

---

## Связанность

Любое знание существует не изолированно.

Оно всегда может иметь связи с другими знаниями.

---

# Жизненный цикл знания

Любой Knowledge Object проходит одинаковый путь.

```
Источник

↓

Perception

↓

Normalization

↓

Understanding

↓

Knowledge Object

↓

Memory

↓

Working Memory

↓

Reasoning

↓

Learning

↓

Memory
```

В процессе жизни объект может многократно изменяться.

---

# Основные свойства знания

Любой объект знаний обязан обладать следующими свойствами.

## Идентичность

Каждый объект имеет уникальный идентификатор.

Идентификатор никогда не изменяется.

---

## Тип

Каждый объект принадлежит одному конкретному типу.

Например:

Concept

Fact

Rule

Definition

Goal

Question

Algorithm

...

Тип определяет семантику объекта.

---

## Содержимое

Каждый объект хранит собственное содержание.

Это может быть:

текст;

формула;

структура;

код;

описание;

значение;

процедура.

Формат содержимого определяется типом объекта.

---

## Связи

Каждый объект может иметь произвольное количество связей.

Связи являются такими же важными, как сам объект.

Большинство рассуждений работают именно через связи.

---

## Метаданные

Каждый объект хранит информацию о себе.

Например:

время создания;

источник;

автор;

уверенность;

приоритет;

частота использования.

---

## Версия

Объект способен изменяться.

При этом должна существовать возможность определить его актуальную версию.

---

# Knowledge Object

Каждый объект знаний концептуально состоит из следующих частей.

```
Knowledge Object

├── Identity

├── Type

├── Content

├── Metadata

├── Relations

├── Evidence

├── Statistics

└── History
```

Каждый раздел будет подробно описан далее.

---

# Identity

Identity отвечает только за идентификацию объекта.

Identity никогда не содержит знаний.

Он включает:

- уникальный идентификатор;
- внутренний тип;
- версию;
- состояние.

Identity никогда не изменяет смысл объекта.

---

# Type

Type определяет семантику объекта.

Например:

Concept

Definition

Fact

Rule

Goal

Question

Algorithm

Procedure

Episode

Observation

...

Тип определяет:

как объект создаётся;

как он изменяется;

как участвует в рассуждении.

Тип не определяет способ хранения.

---

# Content

Content содержит непосредственно знание.

Например.

Для Definition —

само определение.

Для Rule —

условие и следствие.

Для Algorithm —

описание алгоритма.

Для Fact —

утверждение.

Для Concept —

описание понятия.

Именно Content является смысловой частью объекта.

---

# Metadata

Metadata не является знанием.

Она описывает знание.

Например:

источник;

время создания;

дата последнего изменения;

автор;

уровень доверия;

уровень важности;

частота использования;

степень проверки.

Метаданные никогда не участвуют напрямую в рассуждении.

Они влияют только на выбор знаний.

---

# Relations

Ни один объект не существует отдельно.

Каждый объект способен иметь связи с другими объектами.

Например:

определяет;

использует;

является частью;

является примером;

противоречит;

обобщает;

специализирует.

Список отношений определяется отдельно.

---

# Evidence

Каждое знание должно иметь подтверждения.

Подтверждением могут являться:

книга;

статья;

RFC;

документация;

эксперимент;

собственный опыт;

несколько независимых источников.

Система должна различать знание и степень уверенности в нём.

---

# Statistics

Каждый объект постепенно накапливает статистику.

Например:

сколько раз использовался;

сколько раз оказался полезным;

сколько раз участвовал в выводах;

сколько раз приводил к ошибкам;

когда использовался последний раз.

Эта информация используется Learning.

---

# History

История позволяет проследить эволюцию знания.

История может содержать:

создание;

изменение;

объединение;

разделение;

удаление;

изменение уровня доверия.

История не используется при обычном поиске.

Она необходима для анализа и восстановления.
---

# Типы знаний

Несмотря на то, что внутри системы существует только один универсальный объект — Knowledge Object, смысл каждого объекта определяется его типом.

Тип задаёт семантику знания.

Тип не определяет способ хранения.

Тип не определяет внутреннюю структуру памяти.

Тип определяет только значение объекта.

---

# Основные категории знаний

Все знания NeuroCore делятся на несколько фундаментальных категорий.

```
Knowledge

├── Concept
├── Definition
├── Fact
├── Property
├── Relation
├── Rule
├── Constraint
├── Algorithm
├── Procedure
├── Goal
├── Task
├── Question
├── Hypothesis
├── Prediction
├── Observation
├── Episode
├── Experience
├── Skill
├── Error
└── Source
```

Этот список является минимальным ядром архитектуры.

В дальнейшем могут появляться специализированные типы, но все они должны наследовать поведение одного из перечисленных.

---

# Concept

Concept является самым фундаментальным типом знания.

Concept отвечает на вопрос

> Что это такое?

Concept описывает существование некоторой сущности.

Например

```
Integer

Function

Network

Socket

Door

Gravity

Memory

Compiler

Human
```

Concept сам по себе ничего не утверждает.

Он лишь сообщает системе, что данная сущность существует.

---

## Что хранит Concept

Concept может содержать

- название;
- краткое описание;
- категорию;
- синонимы;
- область знаний.

Все остальные знания должны ссылаться на Concept.

---

## Что НЕ хранит Concept

Concept не хранит

определения;

правила;

свойства;

алгоритмы;

ограничения.

Для этого существуют другие типы объектов.

---

# Definition

Definition отвечает на вопрос

> Что означает данное понятие?

Definition всегда принадлежит некоторому Concept.

Например

```
Stack

↓

Definition

Структура данных,
работающая по принципу LIFO.
```

Для одного Concept может существовать несколько определений.

Каждое определение имеет собственный источник.

---

# Fact

Fact отвечает на вопрос

> Что является истинным?

Fact представляет собой утверждение.

Например

```
Earth

orbits

Sun
```

или

```
TCP

uses

ports
```

Fact может быть

истинным;

ложным;

непроверенным;

оспариваемым.

Истинность определяется уровнем доверия, а не типом объекта.

---

# Property

Property описывает характеристику объекта.

Например

```
Sky

color

blue
```

или

```
Water

boiling point

100 °C
```

или

```
TCP

reliable

true
```

Property отличается от Fact.

Fact утверждает существование связи.

Property описывает качество объекта.

---

# Relation

Relation описывает связь между двумя знаниями.

Relation никогда не существует самостоятельно.

Она всегда соединяет объекты памяти.

Например

```
Compiler

implements

Parser
```

или

```
Cat

is_a

Animal
```

или

```
Function

uses

Variable
```

Relation является объектом первого класса.

Она имеет собственные свойства.

Например

уровень доверия;

источник;

дату появления;

приоритет.

---

# Rule

Rule отвечает на вопрос

> Что должно происходить?

Rule состоит минимум из двух частей.

```
Condition

↓

Action
```

или

```
If

↓

Then
```

Например

```
If

socket closed

↓

send error
```

или

```
If

temperature < 0

↓

water freezes
```

Rule может использоваться Planner и Reasoning.

---

# Constraint

Constraint определяет ограничения.

Например

```
Division

cannot divide by zero
```

или

```
Password

minimum length

8
```

Constraint отличается от Rule.

Rule описывает поведение.

Constraint запрещает некоторые состояния.

---

# Algorithm

Algorithm отвечает на вопрос

> Как выполнить задачу?

Algorithm является объектом памяти.

Он не является частью программы.

Он может хранить

последовательность действий;

используемые знания;

ограничения;

оценку успешности.

Reasoning выбирает Algorithm.

Execution его выполняет.

Learning способен изменять его эффективность.

---

# Procedure

Procedure похожа на Algorithm.

Но существует важное отличие.

Algorithm описывает общий способ решения.

Procedure описывает конкретную последовательность действий.

Например

```
Как установить Ubuntu.
```

или

```
Как сварить борщ.
```

Procedure ориентирована на выполнение.

Algorithm ориентирован на решение класса задач.

---

# Goal

Goal описывает желаемое состояние.

Goal отвечает на вопрос

> Чего нужно достичь?

Например

```
Compile project

Fix bug

Cook dinner

Find exploit
```

Planner работает именно с Goal.

---

# Task

Task представляет собой конкретную работу.

Task появляется после декомпозиции Goal.

Например

```
Goal

↓

Write compiler

↓

Tasks

Lexer

Parser

Optimizer

Codegen
```

Task может создавать новые Task.

---

# Question

Question представляет отсутствие знаний.

Question не является ошибкой.

Наоборот.

Question запускает процесс мышления.

Например

```
Почему?

Как?

Что?

Где?

Когда?

Зачем?
```

После получения ответа Question может породить новые знания.

---

# Hypothesis

Hypothesis представляет предполагаемое знание.

Она ещё не считается истинной.

Например

```
Возможно

сервер использует nginx.
```

или

```
Вероятно

эта функция вызывает утечку памяти.
```

Hypothesis используется Reasoning.

После проверки может стать Fact.

---

# Prediction

Prediction является гипотезой о будущем.

Например

```
Если выполнить X,

вероятно получится Y.
```

Prediction используется Planner и Simulation.

---

# Observation

Observation представляет результат восприятия.

Например

```
Я увидел

ошибку.

```

или

```
Температура

38°C.
```

Observation ещё не является Fact.

Несколько Observation могут подтвердить Fact.

---

# Episode

Episode представляет завершённое событие.

Например

```
Компиляция проекта.

Разговор.

Обучение.

Пентест.

Запуск программы.
```

Episode связывает между собой множество объектов знаний.

Episode является основой эпизодической памяти.

---

# Experience

Experience представляет выводы, полученные из Episode.

Например

```
После пяти запусков

данный алгоритм оказался быстрее.
```

Experience возникает не сразу.

Он является результатом анализа множества Episode.

---

# Skill

Skill представляет способность выполнять некоторый класс задач.

Skill объединяет

алгоритмы;

процедуры;

опыт;

статистику.

Например

```
Reverse Engineering

Web Pentest

Cooking

Programming

Mathematics
```

Skill постоянно развивается.

---

# Error

Error является полноценным объектом знаний.

Ошибка не удаляется.

Она хранится.

Например

```
Компиляция завершилась ошибкой.

Алгоритм дал неверный ответ.

Reasoning построил ложную гипотезу.
```

Learning использует Error для улучшения памяти.

---

# Source

Source описывает происхождение знаний.

Source никогда не является самим знанием.

Например

```
Книга

RFC

Wikipedia

GitHub

StackOverflow

Учебник

Эксперимент

Пользователь

LLM

Собственное наблюдение
```

Source используется только для оценки доверия и объяснимости.

---

# Почему типов именно столько

Данные типы покрывают практически все виды знаний, с которыми сталкивается человек.

Большинство специализированных объектов являются комбинациями базовых типов.

Например.

Математическая теорема:

Concept

+

Definition

+

Rule

+

Evidence

+

Source

Рецепт приготовления:

Goal

+

Procedure

+

Constraint

+

Algorithm

Исходный код функции:

Concept

+

Procedure

+

Algorithm

+

Relation

Благодаря этому архитектура остаётся небольшой, но способной представлять знания практически любой предметной области.
---

# Связи между знаниями

Изолированное знание имеет ограниченную ценность.

Интеллект возникает не из количества знаний, а из количества и качества связей между ними.

Поэтому связи являются объектами первого класса и рассматриваются как равноправная часть памяти.

Без связей Memory превращается в архив.

Со связями Memory становится когнитивной системой.

---

# Общая модель связи

Любая связь соединяет минимум два объекта знаний.

```
Knowledge Object

↓

Relation

↓

Knowledge Object
```

Связь сама является Knowledge Object.

Она имеет:

- собственный идентификатор;
- собственный источник;
- собственную уверенность;
- собственную историю;
- собственную статистику.

Удаление объекта автоматически не означает удаление всех связей.

Каждая связь должна проверяться отдельно.

---

# Направление связей

Связи могут быть:

- направленными;
- двунаправленными.

Например

```
Compiler

implements

Parser
```

имеет направление.

А

```
Cat

similar_to

Tiger
```

может быть двунаправленной.

Тип связи определяет её поведение.

---

# Базовые типы отношений

Архитектура определяет минимальный набор универсальных отношений.

---

## is_a

Описывает наследование или принадлежность к классу.

Пример

```
Cat

is_a

Animal
```

---

## instance_of

# Семантическая сила связи

Каждая связь имеет степень силы.

Например

```
0.0

нет связи

↓

1.0

максимально сильная связь
```

Сила связи изменяется Learning.

Часто используемые связи постепенно усиливаются.

Неиспользуемые постепенно ослабевают.

---

# Доверие

Каждая связь имеет собственную уверенность.

Это важно.

Например

```
Cat

is_a

Animal
```

имеет практически абсолютную уверенность.

А

```
This service

probably uses

Redis
```

имеет значительно меньшую.

Reasoning обязан учитывать доверие.

---

# Источник связи

Любая связь знает своё происхождение.

Например

```
RFC

Wikipedia

Book

Experiment

Observation

LLM

User
```

Один и тот же факт может иметь несколько независимых источников.

Это увеличивает доверие.

---

# Версионирование

Связи также изменяются.

Например

```
Library A

depends_on

Library B
```

После обновления проекта зависимость может исчезнуть.

История изменения связи должна сохраняться.

---

# Противоречия

Memory допускает существование противоречащих знаний.

Например

```
Source A

↓

Sky is green

Source B

↓

Sky is blue
```

Оба знания могут существовать одновременно.

Memory не удаляет автоматически противоречия.

Обнаружение и разрешение противоречий выполняют Understanding, Reasoning и Learning.

---

# Дубликаты

Во время импорта новых знаний система обязана проверять:

- идентичность;
- эквивалентность;
- семантическую близость.

Если объект уже существует,

создаётся не новый объект,

а обновляется существующий.

Если автоматическое объединение невозможно,

создаётся конфликт, который должен быть разрешён позже.

---

# Идентичность

Knowledge Object никогда не меняет свой идентификатор.

Даже если:

- изменилось описание;
- изменился уровень доверия;
- добавились новые источники;
- появились новые связи.

Создание нового идентификатора допускается только тогда, когда создаётся действительно новое знание.

---

# Доверие к знаниям

Каждый объект имеет числовую оценку доверия.

Например

```
0.0

неизвестно

0.25

слабое предположение

0.50

правдоподобно

0.75

хорошо подтверждено

1.00

максимальная уверенность
```

Это не вероятность.

Это степень доверия системы к знанию.

---

# Факторы доверия

На доверие влияют:

- количество независимых источников;
- качество источников;
- результаты собственного опыта;
- успешность использования;
- отсутствие противоречий;
- подтверждение другими знаниями.

Learning постоянно пересчитывает доверие.

---

# Активация

Во время поиска не вся память становится активной.

Каждый объект имеет уровень активации.

При решении задачи активируются только знания, связанные с текущим контекстом.

Активация распространяется по связям.

Чем сильнее связь,

тем выше вероятность активации соседнего объекта.

---

# Забывание

Неиспользуемые знания не обязаны удаляться.

Они могут:

- терять активацию;
- снижать приоритет;
- архивироваться;
- сжиматься.

Удаление является крайней мерой.

Главная цель — сохранить знания, но уменьшить стоимость поиска.

---

# Инварианты модели знаний

Следующие правила являются обязательными.

- Каждый объект имеет уникальный идентификатор.
- Каждый объект имеет ровно один основной тип.
- Каждый объект может иметь произвольное количество связей.
- Каждая связь является самостоятельным объектом.
- Каждый объект знает своё происхождение.
- Каждый объект имеет уровень доверия.
- Каждый объект может участвовать в рассуждении.
- Любой объект может быть изменён без нарушения целостности памяти.
- Все подсистемы работают исключительно через Knowledge Object.
- Никакая подсистема не имеет собственных внутренних представлений знаний.

---
# Жизненный цикл Knowledge Object

Каждый объект знаний проходит одинаковый жизненный цикл.

Независимо от того, является ли объект определением, алгоритмом, гипотезой или событием.

```
Created

↓

Validated

↓

Stored

↓

Linked

↓

Activated

↓

Used

↓

Updated

↓

Archived

↓

Deleted (optional)
```

Удаление является последней стадией.

Большинство знаний никогда не удаляются полностью.

---

# Stage 1. Created

Объект впервые появился.

Источник может быть любым:

- Understanding;
- пользователь;
- импорт базы знаний;
- внешний API;
- собственное рассуждение;
- результат выполнения;
- Learning.

На данном этапе объект ещё не считается частью памяти.

---

# Stage 2. Validation

Проверяется корректность объекта.

Минимальные требования:

- существует идентификатор;
- определён тип;
- присутствует содержимое;
- указан источник;
- отсутствуют критические ошибки.

При невозможности проверки объект получает статус Invalid.

---

# Stage 3. Storage

После успешной проверки объект помещается в долговременную память.

На данном этапе:

- создаются индексы;
- сохраняются метаданные;
- записываются свойства;
- формируются базовые связи.

---

# Stage 4. Linking

После сохранения система пытается найти связи.

Например:

- похожие знания;
- родительские понятия;
- дочерние понятия;
- связанные алгоритмы;
- определения;
- правила;
- ограничения.

Количество связей постепенно увеличивается.

---

# Stage 5. Activation

Во время решения задачи объект может стать активным.

Активный объект попадает в Working Memory.

После завершения задачи объект снова становится неактивным.

Память не копирует знания.

Working Memory содержит ссылки на объекты долговременной памяти.

---

# Stage 6. Usage

Каждое использование объекта фиксируется.

Обновляются:

- время последнего использования;
- количество обращений;
- успешность применения;
- статистика вывода.

Learning использует эти данные.

---

# Stage 7. Update

Любой объект может изменяться.

Например:

- появилось новое определение;
- увеличилось доверие;
- появился новый источник;
- изменилась статистика;
- были добавлены новые связи.

При обновлении идентификатор объекта сохраняется.

---

# Stage 8. Archive

Редко используемые знания могут архивироваться.

Архивация не означает удаление.

Архивированные объекты:

- сохраняются;
- участвуют в поиске;
- имеют меньший приоритет;
- не занимают ресурсы Working Memory.

---

# Stage 9. Delete

Удаление используется только в исключительных случаях.

Например:

- объект признан ошибочным;
- импорт оказался повреждён;
- обнаружен полный дубликат;
- пользователь удалил знания.

Даже после удаления желательно сохранять запись об истории объекта.

---

# Требования к реализации

Данный документ не определяет конкретные структуры данных языка C.

Однако любая реализация должна удовлетворять следующим требованиям.

---

## Независимость хранения

Knowledge Object не должен зависеть от:

- LMDB;
- SQLite;
- PostgreSQL;
- файлов;
- формата сериализации.

Хранилище является заменяемым компонентом.

---

## Независимость памяти

Knowledge Object не должен содержать указатели, зависящие от конкретного процесса.

Все внутренние ссылки должны использовать стабильные идентификаторы.

Это позволяет:

- сериализовать память;
- переносить базы;
- выполнять репликацию;
- работать в нескольких процессах.

---

## Расширяемость

Добавление нового типа знаний не должно требовать изменения существующих типов.

Архитектура должна поддерживать открытое множество типов.

---

## Масштабируемость

Количество объектов знаний заранее неизвестно.

Архитектура должна быть рассчитана на хранение:

- миллионов объектов;
- десятков миллионов связей;
- больших графов предметных областей.

---

# Требования к Memory API

Memory является единственным владельцем объектов знаний.

Другие подсистемы не имеют права изменять память напрямую.

Все операции выполняются через API.

Минимальный набор операций:

```
Create()

Read()

Update()

Delete()

Find()

Search()

Link()

Unlink()

Activate()

Deactivate()

Import()

Export()

Validate()
```

Reasoning, Planner и Learning используют только этот интерфейс.

---

# Работа с идентификаторами

Каждый объект получает глобально уникальный идентификатор.

Идентификатор:

- не изменяется;
- не зависит от адреса памяти;
- используется всеми подсистемами;
- используется во всех связях.

Ни одна подсистема не должна использовать физические адреса объектов как средство идентификации.

---

# Работа с версиями

Каждое изменение увеличивает номер версии объекта.

Предыдущие версии могут сохраняться.

Это позволяет:

- анализировать развитие знаний;
- выполнять откат;
- сравнивать изменения;
- объяснять происхождение выводов.

---

# Требования к поиску

Поиск знаний должен поддерживать несколько режимов.

Минимальный набор:

- поиск по идентификатору;
- поиск по типу;
- поиск по имени;
- поиск по содержимому;
- поиск по отношениям;
- поиск по источнику;
- поиск по уровню доверия;
- поиск по времени;
- поиск по статистике;
- семантический поиск.

Конкретные алгоритмы поиска определяются Memory.

---

# Требования к Learning

Learning не создаёт собственную память.

Learning изменяет существующие объекты.

Learning может:

- изменять доверие;
- усиливать связи;
- ослаблять связи;
- добавлять статистику;
- создавать новые связи;
- объединять знания;
- помечать противоречия.

Learning не имеет права изменять смысл знания без достаточных оснований.

---

# Требования к Reasoning

Reasoning работает только с объектами знаний.

Reasoning не обращается к:

- PDF;
- тексту;
- HTML;
- JSON;
- изображениям.

Любое рассуждение начинается после завершения этапов Perception и Understanding.

---

# Требования к Planner

Planner получает:

- Goal;
- Working Memory;
- ограничения;
- доступные алгоритмы;
- доступные процедуры.

Planner не анализирует исходные источники информации.

---

# Требования к Execution

Execution получает готовый план.

Execution отвечает только за выполнение действий и регистрацию результата.

Execution не принимает логических решений.

---

# Требования к Understanding

Understanding является единственной подсистемой, которая преобразует внешнюю информацию в объекты знаний.

Никакая другая подсистема не должна создавать Knowledge Object напрямую из исходных данных.

---

# Архитектурные инварианты

Следующие утверждения обязательны для всей системы.

1. Внутри NeuroCore существуют только Knowledge Object.
2. Все знания имеют единое внутреннее представление.
3. Все подсистемы работают через Memory API.
4. Источник информации никогда не используется напрямую после этапа Understanding.
5. Любое рассуждение выполняется только над объектами знаний.
6. Любое изменение знаний проходит через Memory.
7. Любое знание имеет происхождение.
8. Любое знание имеет уровень доверия.
9. Любое знание может иметь связи с другими знаниями.
10. Архитектура не зависит от конкретной реализации хранилища или модели ИИ.

---

# Заключение

Модель знаний является фундаментом NeuroCore.

Все остальные подсистемы — Memory, Reasoning, Planner, Learning, Execution и VM — строятся поверх неё.

Изменения модели знаний оказывают влияние на всю архитектуру проекта.

Поэтому данный документ рассматривается как один из основных архитектурных стандартов системы и должен изменяться только при наличии веских инженерных оснований.
