# Understanding

Version: 1.0

---

# Назначение

Understanding является единственной подсистемой NeuroCore, которая превращает внешнюю информацию в внутренние знания.

Она является мостом между внешним миром и Memory.

Все остальные подсистемы работают исключительно с Knowledge Objects.

Если информация не прошла через Understanding — она не существует для NeuroCore.

---

# Главная задача

Преобразовать любую информацию независимо от её источника в Knowledge Objects.

```
External Data

↓

Understanding

↓

Knowledge Objects

↓

Memory
```

Understanding ничего не знает о Reasoning, Planner или Execution.

Его единственная задача — понять входную информацию.

---

# Главный принцип

Любой источник проходит одинаковый путь обработки.

Не существует отдельных архитектур для:

- PDF;
- книг;
- HTML;
- Markdown;
- программного кода;
- изображений;
- видео;
- аудио;
- диалога;
- API.

Меняются только первые этапы обработки.

Все заканчивается созданием одинаковых Knowledge Objects.

---

# Архитектура

```
                Understanding

                      │

              Source Adapters

                      │

               Normalization

                      │

            Structural Analysis

                      │

            Semantic Analysis

                      │

         Knowledge Construction

                      │

           Conflict Detection

                      │

           Knowledge Validation

                      │

            Memory Integration
```

Каждый этап имеет единственную ответственность.

---

# Pipeline

Understanding всегда работает как конвейер.

```
Receive

↓

Normalize

↓

Analyze

↓

Extract

↓

Build

↓

Validate

↓

Merge

↓

Store
```

Никакие этапы не пропускаются.

---

# Stage 1. Source Adapters

Источник информации преобразуется во внутренний формат.

Например

```
PDF

↓

Text
```

```
Image

↓

OCR

↓

Text
```

```
Speech

↓

Speech-to-Text

↓

Text
```

```
C Source

↓

AST
```

```
Git Repository

↓

Project Structure
```

После этого формат источника перестает иметь значение.

---

# Stage 2. Normalization

Нормализация удаляет особенности конкретного источника.

Например

- HTML-теги;
- Markdown-разметку;
- PDF-разрывы страниц;
- OCR-ошибки;
- служебные символы;
- дубликаты.

Результатом становится нормализованное представление.

---

# Stage 3. Structural Analysis

Система определяет структуру документа.

Например

- главы;
- разделы;
- функции;
- классы;
- таблицы;
- списки;
- блоки кода;
- формулы;
- изображения;
- подписи.

На этом этапе смысл ещё не извлекается.

---

# Stage 4. Semantic Analysis

Определяется смысл информации.

Например обнаруживаются:

- понятия;
- определения;
- факты;
- свойства;
- правила;
- ограничения;
- алгоритмы;
- процедуры;
- цели;
- вопросы;
- гипотезы;
- события;
- зависимости.

Именно здесь начинается понимание.

---

# Stage 5. Knowledge Construction

На основании семантического анализа создаются Knowledge Objects.

Например

```
Concept

↓

Compiler
```

```
Definition

↓

Compiler is...
```

```
Rule

↓

If ...

Then ...
```

```
Algorithm

↓

QuickSort
```

Каждый объект получает:

- тип;
- содержимое;
- источник;
- первоначальную уверенность;
- ссылки на контекст.

---

# Stage 6. Conflict Detection

Перед сохранением выполняется поиск конфликтов.

Проверяются:

- полные дубликаты;
- семантические дубликаты;
- противоречия;
- несовместимые определения;
- несовместимые правила;
- конфликтующие свойства.

Understanding ничего не удаляет.

Он только сообщает Memory о найденных конфликтах.

---

# Stage 7. Knowledge Validation

Каждый объект проходит проверку.

Минимальные требования:

- определён тип;
- существует содержимое;
- существует источник;
- отсутствуют критические ошибки;
- объект соответствует модели Knowledge.

Некорректные объекты не сохраняются.

---

# Stage 8. Memory Integration

После успешной проверки объекты передаются Memory.

Memory самостоятельно:

- назначает идентификаторы;
- создаёт связи;
- обновляет индексы;
- объединяет существующие знания;
- сохраняет историю.

Understanding не изменяет память напрямую.

---

# Source Adapters

Каждый источник обслуживается отдельным адаптером.

Например

```
PDF Adapter

Markdown Adapter

HTML Adapter

Code Adapter

Image Adapter

Speech Adapter

Video Adapter

Git Adapter

API Adapter

Chat Adapter
```

Все адаптеры реализуют единый интерфейс.

---

# Структурный анализ

Структурный анализ отвечает только за форму информации.

Например для исходного кода он определяет:

- функции;
- классы;
- структуры;
- перечисления;
- зависимости;
- пространство имён.

Для книги:

- главы;
- разделы;
- подпункты;
- примечания;
- ссылки.

---

# Семантический анализ

Семантический анализ отвечает на вопрос:

> Что означает эта информация?

Он никогда не отвечает на вопрос:

> Что делать дальше?

Этим занимаются другие подсистемы.

---

# Использование LLM

LLM не является ядром Understanding.

Она является внешним инструментом.

LLM может использоваться для:

- извлечения определений;
- поиска отношений;
- классификации;
- анализа естественного языка;
- построения кратких объяснений.

Если завтра LLM изменится,

Understanding продолжит работать через тот же интерфейс.

---

# Использование правил

Не вся обработка должна выполняться LLM.

Многие задачи эффективнее решаются детерминированными алгоритмами.

Например

- разбор AST;
- анализ Markdown;
- извлечение ссылок;
- поиск URL;
- поиск импортов;
- анализ структуры проекта.

Understanding должен максимально использовать специализированные анализаторы там, где это возможно.

---

# Инварианты

Understanding обязан соблюдать следующие правила.

- Не изменяет Memory напрямую.
- Не выполняет рассуждений.
- Не принимает решений.
- Не планирует действия.
- Не обращается к Planner.
- Не обращается к Execution.
- Не создает собственные форматы знаний.
- Создает только Knowledge Objects.
- Работает через единый Pipeline.
- Любой источник проходит одинаковые стадии обработки.

---

# Заключение

Understanding является единственной подсистемой, которая превращает внешний мир в внутренние знания.

Он не хранит знания, не делает выводов и не принимает решений.

Его задача — обеспечить, чтобы любая информация независимо от происхождения была преобразована в качественные, непротиворечивые и пригодные для дальнейшей работы Knowledge Objects.
