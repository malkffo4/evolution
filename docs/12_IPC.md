# IPC

Version: 1.0

---

# Назначение

IPC (Inter-Process Communication) является единой системой обмена сообщениями внутри NeuroCore.

Несмотря на название, IPC используется не только между процессами.

Он обеспечивает взаимодействие между всеми компонентами системы независимо от того, находятся ли они:

- в одном потоке;
- в разных потоках;
- в разных процессах;
- на разных машинах (в будущем).

IPC является единственным способом общения компонентов.

---

# Главный принцип

Никакие два компонента NeuroCore не должны знать друг о друге напрямую.

Неправильно

```
Reasoning

↓

Planner
```

Правильно

```
Reasoning

↓

IPC

↓

Planner
```

Это уменьшает связанность архитектуры.

---

# Основные цели

IPC обеспечивает:

- передачу сообщений;
- передачу событий;
- маршрутизацию;
- очереди;
- публикацию событий;
- подписку;
- логирование;
- масштабируемость.

---

# Архитектура

```
                 IPC

                  │

          Message Router

                  │

    ┌─────────────┼─────────────┐

    │             │             │

 Message Bus   Event Bus    Queue Manager

    │             │             │

    └─────────────┼─────────────┘

                  │

        All NeuroCore Modules
```

# Подключённые компоненты

Через IPC работают:

```
Runtime

Memory

Understanding

Reasoning

Planner

Execution

Learning

VM

Tools

Plugins
```

Любой новый модуль автоматически использует IPC.

---

# Типы взаимодействия

IPC поддерживает несколько моделей.

---

## Request / Response

```
Module A

↓

Request

↓

Module B

↓

Response
```

Используется для синхронных операций.

---

## Event

```
Module

↓

Event

↓

IPC

↓

Subscribers
```

Используется для уведомлений.

---

## Publish / Subscribe

```
Publisher

↓

Topic

↓

Subscribers
```

Компоненты не знают друг о друге.

---

## Queue

```
Producer

↓

Queue

↓

Consumer
```

Используется для длительных операций.

---

# Message

Каждое сообщение имеет одинаковую структуру.

```
Message

├── ID
├── Type
├── Sender
├── Receiver
├── Timestamp
├── Priority
├── Payload
├── Context
└── Metadata
```

Все сообщения имеют единый формат.

---

# Event

Event отличается от Message.

Message ожидает обработчика.

Event публикуется без знания получателя.

Например

```
KnowledgeCreated

TaskFinished

GoalCompleted

MemoryUpdated

PluginLoaded
```

---

# Topics

События публикуются в Topics.

Например

```
memory.*

reasoning.*

planner.*

runtime.*

execution.*

learning.*

plugin.*
```

Подписчик может получать только интересующие темы.

---

# Приоритет сообщений

IPC поддерживает несколько уровней.

```
Critical

High

Normal

Low

Background
```

Маршрутизатор обрабатывает сообщения согласно приоритету.

---

# Очереди

Каждый компонент имеет собственную очередь сообщений.

Например

```
Planner Queue

Reasoning Queue

Execution Queue

Learning Queue
```

Это позволяет избежать взаимных блокировок.

---

# Message Router

Router отвечает за доставку сообщений.

Он знает:

- зарегистрированные компоненты;
- их состояние;
- доступность;
- очереди.

Router не анализирует содержимое сообщений.

---

# Event Bus

Event Bus распространяет события.

Например

```
Execution

↓

TaskFinished

↓

Event Bus

↓

Learning

↓

Memory

↓

Logger
```

Одно событие может иметь множество подписчиков.

---

# Queue Manager

Queue Manager отвечает за:

- создание очередей;
- удаление очередей;
- управление размером;
- контроль переполнения;
- повторную доставку.

---

# Регистрация компонентов

Каждый компонент при запуске регистрируется.

```
Runtime

↓

IPC Register

↓

Router
```

После регистрации компонент может отправлять сообщения.

---

# Discovery

IPC знает только интерфейсы.

Компоненты обнаруживаются автоматически после регистрации.

Это позволяет подключать плагины без изменения существующего кода.

---

# Надёжность

Каждое сообщение имеет статус.

```
Created

Queued

Delivered

Processing

Completed

Failed

Expired
```

Это позволяет отслеживать жизненный цикл сообщений.

---

# Timeout

Любой Request может иметь таймаут.

При превышении времени ожидания:

- создаётся Error;
- отправитель получает уведомление;
- сообщение помечается как Failed.

---

# Retry

IPC поддерживает повторную доставку.

Например

```
Send

↓

Timeout

↓

Retry

↓

Success
```

Политика Retry определяется Runtime.

---

# Broadcast

Некоторые сообщения рассылаются всем компонентам.

Например

```
Shutdown

ConfigurationUpdated

LowMemory

PluginLoaded
```

---

# Фильтрация

Подписчики могут фильтровать сообщения.

Например

```
memory.*

planner.*

runtime.error.*

execution.finished.*
```

Это уменьшает нагрузку.

---

# Асинхронность

По умолчанию IPC работает асинхронно.

Синхронные запросы используются только там, где это действительно необходимо.

---

# Безопасность

Компоненты не имеют права изменять чужие сообщения.

После публикации сообщение становится неизменяемым.

Если требуется изменение,

создаётся новое сообщение.

---

# Журналирование

Все сообщения могут журналироваться.

Минимально сохраняются:

- отправитель;
- получатель;
- время;
- тип;
- длительность обработки;
- результат.

Это облегчает отладку системы.

---

# Производительность

IPC должен обеспечивать:

- минимальные задержки;
- отсутствие глобальных блокировок;
- потокобезопасность;
- пакетную обработку сообщений;
- возможность масштабирования.

---

# Инварианты

IPC обязан гарантировать:

- единый формат сообщений;
- отсутствие прямых вызовов между компонентами;
- корректную маршрутизацию;
- поддержку событий;
- поддержку очередей;
- поддержку публикации и подписки;
- неизменяемость опубликованных сообщений;
- регистрацию всех компонентов.

---

# Заключение

IPC является коммуникационной системой NeuroCore.

Он обеспечивает слабую связанность компонентов, централизованную маршрутизацию сообщений и событий, а также создаёт основу для масштабирования системы от одного процесса до распределённой архитектуры без изменения логики отдельных модулей.
