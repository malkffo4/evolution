# Execution

Version: 1.0

---

# Назначение

Execution является исполнительной подсистемой NeuroCore.

Его задача — безопасно и предсказуемо выполнять планы, построенные Planner.

Execution не принимает решений.

Execution не строит планы.

Execution не выполняет рассуждений.

Execution является "руками" системы.

---

# Главная задача

Преобразовать Plan в последовательность реально выполненных действий.

```
Planner

↓

Plan

↓

Execution

↓

Environment

↓

Result

↓

Memory
```

---

# Главный принцип

Execution никогда самостоятельно не решает, ЧТО делать.

Execution отвечает только за вопрос

> КАК выполнить уже выбранное действие.

Если план невозможно выполнить, Execution сообщает об этом Planner.

---

# Ответственность Execution

Execution отвечает за:

- выполнение действий;
- управление состоянием выполнения;
- контроль ошибок;
- контроль таймаутов;
- взаимодействие с инструментами;
- получение результатов;
- регистрацию событий;
- передачу результатов обратно в Memory.

---

# Что НЕ делает Execution

Execution никогда не:

- извлекает знания;
- понимает документы;
- выбирает алгоритмы;
- строит планы;
- принимает стратегические решения;
- изменяет Knowledge Objects напрямую.

---

# Архитектура

```
                Execution

                    │

          Execution Controller

                    │

        ┌───────────┼───────────┐

        │           │           │

   Step Runner  Tool Manager  State Manager

        │           │           │

        └───────────┼───────────┘

                    │

            Result Collector

                    │

            Event Generator

                    │

               Memory API
```

Каждый компонент имеет одну ответственность.

---

# Общий цикл

```
Получить Plan

↓

Подготовить окружение

↓

Выполнить Step

↓

Получить результат

↓

Проверить ошибки

↓

Сохранить событие

↓

Следующий Step

↓

Завершение
```

---

# Входные данные

Execution получает:

- Plan;
- текущий Context;
- доступные инструменты;
- ограничения;
- параметры среды.

---

# Выходные данные

Execution возвращает:

- успешность;
- ошибки;
- новые Observation;
- новые Episode;
- статистику выполнения;
- время выполнения;
- использованные ресурсы.

Все результаты сохраняются через Memory API.

---

# Execution Controller

Главный управляющий компонент.

Отвечает за:

- запуск выполнения;
- остановку;
- паузу;
- продолжение;
- завершение.

Контроллер никогда не выполняет сами действия.

---

# Step Runner

Выполняет один конкретный Step.

```
Plan

↓

Step

↓

Execute

↓

Result
```

Каждый Step является атомарной операцией.

---

# Tool Manager

Execution работает только через инструменты.

Например

```
Filesystem

Network

Python

Shell

Git

Compiler

Database

Browser

LLM

API
```

Tool Manager отвечает за их использование.

---

# Принцип Tool Abstraction

Execution никогда не вызывает внешние системы напрямую.

Все обращения проходят через Tool Interface.

```
Execution

↓

Tool Interface

↓

Concrete Tool
```

Это позволяет заменять реализации без изменения Execution.

---

# State Manager

Следит за текущим состоянием выполнения.

Например

```
Idle

Running

Paused

Waiting

Retry

Completed

Failed

Cancelled
```

В каждый момент времени Execution имеет одно состояние.

---

# Контекст выполнения

Execution хранит Runtime Context.

Например

- активные переменные;
- открытые соединения;
- временные файлы;
- результаты предыдущих шагов;
- параметры окружения.

Контекст существует только во время выполнения плана.

---

# Result Collector

Собирает результаты выполнения.

Например

```
stdout

stderr

Exit Code

Return Value

Generated Files

Network Response
```

Result Collector не анализирует результаты.

Он только собирает их.

---

# Event Generator

Каждое действие создаёт события.

Например

```
Step Started

↓

Tool Invoked

↓

Step Finished

↓

Error

↓

Retry

↓

Completed
```

Все события становятся Episode.

---

# Обработка ошибок

Execution не скрывает ошибки.

Каждая ошибка превращается в Knowledge Object типа Error.

Ошибка содержит:

- место возникновения;
- описание;
- стек выполнения;
- используемый инструмент;
- входные параметры;
- время.

---

# Retry

Некоторые ошибки допускают повтор.

Execution поддерживает Retry Policy.

Например

```
Network Timeout

↓

Retry

↓

Success
```

или

```
Compilation Error

↓

No Retry
```

Политика определяется Planner.

---

# Таймауты

Каждый Step может иметь ограничение по времени.

При превышении таймаута:

- выполнение прерывается;
- создаётся Error;
- Planner получает уведомление.

---

# Параллельное выполнение

Execution способен выполнять независимые Step одновременно.

Например

```
Step A

├── Step B

├── Step C

└── Step D

↓

Step E
```

Execution обязан соблюдать зависимости.

---

# Отмена выполнения

Execution поддерживает безопасную остановку.

После отмены:

- ресурсы освобождаются;
- инструменты закрываются;
- события сохраняются;
- Planner получает статус Cancelled.

---

# Наблюдения

Во время выполнения могут появляться новые Observation.

Например

```
HTTP Status 404

↓

Observation
```

или

```
Program exited with code 1

↓

Observation
```

Observation позже могут стать Fact.

---

# Эпизоды

Каждый запуск Execution создаёт Episode.

Episode связывает:

- Goal;
- Plan;
- все Step;
- Observation;
- Error;
- Result.

Learning использует Episode для накопления опыта.

---

# Взаимодействие с Planner

Planner создаёт Plan.

Execution выполняет Plan.

Execution никогда не изменяет Plan самостоятельно.

При необходимости он сообщает Planner о невозможности выполнения.

---

# Взаимодействие с Reasoning

Execution не обращается к Reasoning напрямую.

Если необходим новый вывод,

Execution завершает выполнение и возвращает управление Planner.

---

# Взаимодействие с Learning

Learning анализирует Episode.

На основании выполненных действий он может:

- изменить доверие к Plan;
- изменить доверие к Tool;
- обновить статистику;
- повысить вероятность использования успешных стратегий.

---

# Производительность

Execution должен быть максимально детерминированным.

Основные требования:

- минимальное количество блокировок;
- возможность параллельного выполнения;
- потокобезопасность;
- возможность масштабирования.

---

# Инварианты

Execution обязан соблюдать следующие правила.

- Не принимает стратегических решений.
- Не изменяет Memory напрямую.
- Работает только через Tool Interface.
- Каждый Step имеет состояние.
- Каждая ошибка становится Error.
- Каждый запуск создаёт Episode.
- Все результаты передаются через Memory API.
- Все действия логируются.
- Все ресурсы корректно освобождаются.

---

# Заключение

Execution является исполнительной подсистемой NeuroCore.

Он отвечает исключительно за выполнение уже построенных планов.

Execution не обладает интеллектом в архитектурном смысле — его задача заключается в надёжном, воспроизводимом и контролируемом выполнении действий с последующей регистрацией результатов в системе знаний.
